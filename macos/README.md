# Morin Explorer for macOS

A native macOS file manager, written in Swift against Apple's own frameworks. Morin Explorer is the Mac
sibling of Lorin Explorer for Linux (M for Mac, L for Linux). It is a separate
codebase from the Linux app in this repository (Rust and GTK 4): the two share no code. They share
`spec/`, the feature registry, behaviour scenarios and written contracts that both test suites
execute. See `docs/macos-port-plan.md` and `docs/macos-port-spec.md`.

Licence: GPL-3.0-or-later (`LICENSE`). Bundle identifier `casa.alera.MorinExplorer`. Minimum macOS
14. **Universal**: one build that runs on Intel and Apple silicon.

## Layout

```
MorinExplorer.xcodeproj   generated by tools/gen-xcodeproj.py; committed
App/                      the AppKit app: windows and tabs, list and grid views, sidebar, location
                          bar, status bar, operations, properties, settings (SwiftUI), menus
  Assets.xcassets         the app icon (exported from the Linux icon's artwork; nothing is read from it at build time)
Helper/                   privileged helper (SMAppService daemon) and its launchd plist
Packages/
  ExplorerDomain/         models, ports, navigation, search, operations, clipboard, file types.
                          Imports only Foundation; builds and tests with `swift test`
  ExplorerAdapters/       FileManager, FSEvents, Spotlight, DiskArbitration, libarchive, XPC adapters
  ExplorerSpecRunner/     the scenario runner (library, `spec-runner` CLI and tests)
Tests/UnitTests           TabModel and in-process window behaviour tests
Tests/Performance         p95 budgets (see its README)
Tests/UITests             XCUITests (opt-in; see below)
scripts/                  mac-sync.sh, xcode-test.sh, snapshot.sh, mutate-check.sh, release.sh
```

## Building and testing

On a Mac with Xcode 16:

```sh
for p in ExplorerDomain ExplorerAdapters ExplorerSpecRunner; do (cd Packages/$p && swift test); done
(cd Packages/ExplorerSpecRunner && swift run spec-runner)   # status table + every non-pending scenario
sh scripts/xcode-test.sh                                    # universal build + unit and performance tests
UI=1 sh scripts/xcode-test.sh                               # also the UI tests (see below)
sh scripts/release.sh                                       # universal archive, signed if the environment says how, .dmg
```

From the Linux machine: `macos/scripts/mac-sync.sh` copies this folder and `spec/` to the Mac mini
and runs the same thing there. `macos/scripts/snapshot.sh <folder> <out.png>` launches the built app
and writes a picture of its window (the app draws its own window, so no screen-recording permission
is needed); `-MorinSearch`, `-MorinShow preferences|properties`, `-MorinStateDirectory`,
`-MorinOpen` are the launch arguments it uses.

`xcode-test.sh` runs the unit tests by loading the `.xctest` bundle directly rather than through
`xcodebuild test`: testmanagerd refuses test sessions while Developer mode is off, and the direct
run needs neither Developer mode nor a GUI session and exercises the same code. The UI tests do need
both, enabled once per machine:
`sudo DevToolsSecurity -enable` and `sudo automationmodetool enable-automationmode-without-authentication`.

## Releasing

Tag `macos-vX.Y.Z` (the number must equal `MARKETING_VERSION` in `tools/gen-xcodeproj.py`). The
`release` job in `.gitea/workflows/macos.yml` then runs `scripts/release.sh`: a universal archive,
the helper and the app signed with the Developer ID (`--options runtime`, same team), notarized,
stapled, packed into a `.dmg` and attached to a draft release. The secrets it reads are listed in the
workflow. Without them `release.sh` still builds the universal archive and `.dmg`, ad-hoc signed and
labelled as not for distribution; that path is what has been run.

## Where this differs from the spec

* **Ports are synchronous, not `async`.** Spec 5.2 sketches `async` ports. The domain layer uses
  completion-handler ports and `@MainActor`-free state machines, mirroring the Rust ones, so that a
  scenario can hold a request, answer it from a step, and assert immediately with no scheduler in
  between. `async` is used inside the adapters only.
* **libarchive is the system library,** declared through a hand-written header
  (`Packages/ExplorerAdapters/Sources/CArchive`). The macOS SDK ships the library but not its
  header. It reads and writes zip, 7z and tar.gz (checked on macOS 15, libarchive 3.7.4), so
  nothing is bundled.
* **The Xcode project is generated** (`tools/gen-xcodeproj.py`) with folder-synchronized groups:
  source files are never listed in it.
* **The scenario parser is strict but not a general JSON Schema validator.** It rejects unknown
  keys, unknown `do`/`expect`/`port`/`subject` names (read from `spec/schema/scenario.schema.json`),
  malformed steps and bad overrides.
* **Xcode project name** is `MorinExplorer.xcodeproj` (the spec said `FileExplorer`).

## Status

`spec-runner` prints the live table. All 25 registry features are implemented on macOS: 16 at
**parity** (every scenario passes, plus the macOS UI tests the registry names) and 9 **approximate**
with a note saying exactly how (Spotlight search scope, remote locations excluded for v1, the
privileged helper, native window tabs, AppKit view geometry, drag-and-drop gestures, and so on).
Nothing is pending.

## What cannot be proven on the build machine

The CI runner is an Intel Mac mini running macOS 15 unofficially. It cannot show:

* that the arm64 half runs (it is compiled, not executed);
* Developer ID signing and notarization (no identities);
* `SMAppService` daemon approval (needs a signed build and approval in System Settings);
* UI behaviour on a real GPU. The XCUITests in `Tests/UITests` have run (7 passed on the Intel Mac
  once Developer and Automation mode were on), but only the x86_64 half and not on real hardware;
* the release job (`.gitea/workflows/macos.yml`, tag `macos-v*`): it needs the signing and notary
  secrets, so it has never run. `scripts/release.sh` has, without them.
* mounting and ejecting a real volume from the sidebar, and `NSMetadataQuery` content search against
  a populated Spotlight index.

Each of these is built and marked unverified rather than called done.
